# M10 レポート: 投入先の開始時固定、投入経路の梯子とアプリ別上書き

M9 の実測（Hane でキー経由の貼り付けが一切届かない）を受けて決まった方針「経路の梯子＋アプリ別上書き＋カスタムキー」「投入先は録音開始時のウィンドウに固定」の実装。あわせて、検証環境のリマッパの所在の調査（変更なし）。

## 1. 変更の概要

| 項目 | 内容 |
|---|---|
| 投入先の固定 | 録音開始時に前面ウィンドウとフォーカス中コントロール（hwnd・プロセス名・クラス）を記録し、投入はその対象へ行う。 |
| 経路 | `auto` / `paste-message` / `ctrl-v` / `shift-insert` / `typing` / `custom`。決定の順序は「アプリ別上書き → auto のクラス判定」。 |
| typing | クリップボードを使わず、SendInput の Unicode 文字入力（KEYEVENTF_UNICODE）。改行は LF 文字の入力（Enter キーは送らない）。256 コード単位ずつまとめて送る。 |
| custom | 利用者指定のキー組み合わせ（例 Ctrl+Alt+V）。表記は `+` / `-` 区切り。検証はホットキーと同じ（修飾キー 1 つ以上・重複なし・対応キーのみ）。 |
| 設定 | `insertion.custom_key`、`insertion.app_routes`（後述）。既定のときは書き出さない。 |
| 設定画面 | 「投入先と経路」欄（アプリ別上書きの一覧・追加・選択削除、カスタムキー欄）。以前の「投入方式」の無効なラジオ 2 つは外した。 |
| 仕様書 | `docs/spec-v1.0.md` §4（基本動作 5・6）と §7 を更新。 |

### 1.1 投入先の固定（実装 1）

- `ITextInjector` に `CaptureTarget()`（録音開始時に呼ぶ）と `InjectAsync(text, target, ct)` を追加した（既定実装つきなので、既存の実装・テスト用の代役はそのまま動く）。`SessionCoordinator` は録音開始に成功した時点で投入先を記録し、**最初の投入だけ**が使う。再試行（トレイ）は記録を使わず、その時点の前面ウィンドウを対象とする（従来動作）。
- 記録できない場合は `null` で、従来の「投入時点の前面」に倒れる: 自プロセス・シェル・デスクトップ、およびタスクバー・通知領域のウィンドウ（`Shell_TrayWnd` 等。トレイ操作で録音を始めた場合に前景がこれになりうる）。記録処理が例外を投げても録音は止めず、同様に倒れる。
- 経路ごとの扱い:
  - `paste-message`（auto で標準クラスの場合を含む）: 記録したコントロールへ `WM_PASTE` を直接送る。前面化しない。記録後にコントロールだけ消えた場合は、記録ウィンドウ内の編集コントロール（XAML アイランドの場合）かウィンドウ自体を宛先にする。
  - `ctrl-v` / `shift-insert` / `custom` / `typing`: 送る直前に記録したウィンドウを前面化する。バックグラウンドからの `SetForegroundWindow` は拒否されうるので、直接 → 現在の前面スレッドの入力へ一時的に接続して再試行、の順。前面を確認できなければ**何も送らず**「入力先のウィンドウを前面にできなかったため、入力しませんでした」で失敗する。前面化した直後は、対象スレッドがフォーカスを復元するまで（上限 500 ms）待ってから送る。typing はチャンクごとに前面が記録ウィンドウのままか確かめ、変わっていたら中断する。
  - 前面化したあと、元の前景ウィンドウへは戻さない。
- 記録した対象が無効（ウィンドウが閉じられた、別プロセスのハンドルになった等）のときは、クリップボードにも触れず「入力先のウィンドウが見つかりません」で失敗する。セッションは Failed のままテキストを保持する。

### 1.2 経路と設定（実装 2）

`config.json` の `insertion`（`method` は旧版の項目で維持）:

```json
"insertion": {
  "method": "clipboard",
  "custom_key": { "modifiers": ["Ctrl", "Alt"], "key": "V" },
  "app_routes": [ { "process": "hane", "route": "typing" } ]
}
```

- `process` は exe のベース名。大文字小文字は区別せず、末尾の `.exe` は無視して照合する（設定画面は `.exe` を除いて保存する）。
- 検証（読み込み・保存で共通）: 経路名は 6 つのいずれか、`process` は空でなく 64 文字以内で `\ / : * ? " < > |` と制御文字を含まない、重複不可（大文字小文字を無視）、`custom` を使う上書きがあるなら `custom_key` が必要、`custom_key` は修飾キー 1 つ以上と対応キー。不正値は既存の流儀どおりパスつきのエラー（`insertion.app_routes[1].process` など）で、ファイルは変更しない。
- 既定（上書きなし・カスタムキーなし）のときは両キーを書き出さない（旧版が未知キーとして拒否しないため）。旧版が書いたファイルはそのまま読める。
- 経路の決定: 診断の強制指定 → アプリ別上書き（プロセス名は記録した投入先から取る）→ auto。全体の既定経路を別に持たせることはしていない（指示の順序どおり、上書きが無ければ auto）。
- 診断 `--inject-probe` に `--app-route プロセス名=経路`（繰り返し可）、`--custom-key`、`--config`、`--fixed-target [秒]`、`--text`、`--countdown-seconds` を追加した。`--strategy` は 5 経路を受け付ける（旧名 `send-input` は `ctrl-v` の別名）。結果の `route` は `ctrl-v`（旧 `send-input`）/ `shift-insert` / `custom` / `typing` / `paste-message`。

## 2. 実装 3: リマッパの所在

**特定できた。** Windows 検証環境で常駐しているリマッパは Keyhac（`C:\keyhac\keyhac.exe` として稼働）で、Emacs 風のキー設定（Fakeymacs）が `%APPDATA%\Keyhac\` にある。同梱のサンプル `C:\keyhac\_config.py` ではない（これには `scroll_key` が無い）。

根拠（いずれも読み取りのみ。設定・スクリプトは変更していない）:

- `%APPDATA%\Keyhac\config.py:348` — `fc.scroll_key = ["M-v", "C-v"]`（347 行目のコメントは `None` にすると PageUp / PageDown だけを使う選択肢）。同じ値が `_config_personal.py:142` と `_config_parameter.py:224` にもある。`config.py` は `readConfigPersonal(...)` で `_config_personal.py` の節を読み込む（`config.py:79, 111, 156, 594`）ため、実際にどのファイルの値が効いているかは稼働中の読み込み結果を見ないと断定できないが、3 か所とも同じ値。
- `config.py:2582-2584` — `fc.scroll_key[1]`（= `C-v`）を `keymap_emacs` に scroll_down として割り当てている（`2540` 行目の `C-v` = yank は、この設定で上書きされない場合の既定）。他のキーマップにも同様（`2774-2778`、`3102-3106`）。
- Hane が除外対象でない根拠 — `config.py:230-260` の `fc.not_emacs_target`（Emacs キーバインドにしないアプリ）は WSL・ターミナル・Emacs 等のみで Hane を含まない。`Keyhac` 配下の全 `.py`（43 ファイルのうち設定・拡張の Python）に `hane` / `Zed::Window` の記述は無い（`keyhac.ini` にある 71 件はクリップボード履歴で無関係）。`fc.emacs_target_class`（`config.py:203-207`）は `Edit` / `Button` / `ComboBox` / `ListBox`。
- 再現: このリマッパ常駐下で、Hane のフォーカス中に SendInput の Ctrl+V を送っても貼り付けにならない（M9 の実測）。

## 3. 実測（Windows ARM64、キーリマッパ常駐のまま・停止なし）

対話セッション（スケジュールタスクを `/it` で実行）で、publish した `whisparrot.exe`（ARM64、`--inject-probe`）を使った。判定は probe の `result=` ではなく対象側の内容（メモ帳は UI オートメーションで文書内の投入文字列の増分、Hane は画面と文字数表示）で行った。Hane は M9 と同じ別フォルダー・別の状態保存先で起動した Windows ビルド（x64、ARM64 上のエミュレーション）。

### 3.1 Hane に typing（アプリ別上書き `hane` → `typing`）: 10 / 10

`config.json` の `insertion.app_routes` に `hane=typing` を置き、`--config` で読み込んで 10 回投入した（各回 `HPnn typing あいう` + `\n`）。

| 項目 | 結果 |
|---|---|
| 経路 | 全 10 回 `route_used=typing`、宛先クラス `Zed::Window`、`strategy=typing`（上書きが効いた） |
| 入った回数 | **10 / 10**。最終画面に `HP01` … `HP10` が順に並び、文字数表示が 323 → 473（+150 = 10 回 × 15 文字で一致） |
| クリップボード | 使っていない（`typing` はクリップボードに触れない） |

注意: **改行は入らなかった**。文字列に含めた LF（U+000A）は Hane では改行にならず、10 行ではなく 1 行に連結された（文字数にも改行は数えられていない）。→ §6-1。

### 3.2 メモ帳の従来 3 状態（auto、上書きなし）: 30 / 30

M9 と同じ手順（`inject-probe` を状態ごとに 10 回、対象側の文書内の投入文字列の増分が毎回 1）。

| 状態 | 経路 | 増分 1（二重なし） |
|---|---|---|
| 新規ウィンドウ直後 | paste-message（`InputSiteWindowClass` → `RichEditD2DPT` に解決） | **10 / 10** |
| 同じウィンドウで連続 | 同上 | **10 / 10** |
| 他アプリ（Hane）へ移した後に戻す | 同上（`RichEditD2DPT` / `InputSiteWindowClass` が混在） | **10 / 10** |

M9 の水準（30/30）を維持した。

### 3.3 開始時固定（A で記録 → B へ切り替え → 投入）

`--fixed-target` で、カウントダウン後に投入先 A を記録し、7 秒の待ちの間に別アプリ B へ前面を移してから投入させた（投入時点の前面は B）。

| 経路 | A（記録） | B（投入時の前面） | 結果 |
|---|---|---|---|
| paste-message（`notepad` の上書き） | メモ帳 | Hane | A に **入った**（投入文字列の増分 +1。4 回とも）。B（Hane）の画面は無変化（文字数表示 335 のまま、投入文字列なし）。前面は B のまま（前面化しない）。 |
| typing（`hane` の上書き） | Hane | メモ帳 | A（Hane）に **入った**（`FIXEDTYPINGA`、文字数 323 → 335）。B（メモ帳）の文書は不変。Hane が前面化された（`foreground=brought`）。 |
| typing（`notepad` の上書き） | メモ帳 | Hane | メモ帳が前面化され（`foreground_after` がメモ帳）、`typing` が成功を返した。Hane はメモ帳に隠れたため画素比較はできていない。メモ帳側の文書は、§3.4 の最初のキー落ちのため増分を取れていない（0）。この組み合わせは **未確認**。 |
| 記録後に A を閉じる | メモ帳 | Hane | `Failed 入力先のウィンドウが見つかりません`、`route=none`。B は無変化。クリップボードにも触れない。 |

- 前面化の経路: 診断ログが残っている 3 回では、バックグラウンドからの直接 `SetForegroundWindow` は前面にできず、スレッド入力への一時接続（`how=attach`）で前面にできた（3 / 3）。
- B の無変化は、メモ帳 B は文書全文の比較、Hane B は画面の目視と画素比較（投入中の差 8〜21 サンプル = 描画の揺れ程度）で確認した。

### 3.4 追加の観察（梯子の他の経路、改行）

- **メモ帳の新規タブ直後は、最初の 2 キーイベントが落ちる**（typing 以外の素の SendInput 実験でも再現）。新規タブで `ABCDEFGHあい` を Unicode 入力すると `CDEFGHあい` になる（一括でも 5 ms 間隔でも同じ）。同じタブでの 2 回目は全部入る。このため、新規タブへの `typing` / `shift-insert` / `custom` はメモ帳では確かな成否を取れなかった（`shift-insert` と `custom`（Shift+Insert）を各 3 回: 0 / 3、0 / 3。キーが落ちた可能性と、リマッパの影響の切り分けはできていない）。メモ帳は auto（paste-message）が 30 / 30 なので、上書きは不要。
- Unicode 入力の LF / CR は、メモ帳・Hane のどちらでも改行にならない（Hane: `NL1` LF `NL2` と ` CR1` CR `CR2` が改行なしで連結。メモ帳: LF が落ちる）。→ §6-1。

## 6. 判断が必要な点・未検証・限界

1. **Hane に typing で入れたテキストは改行が失われる。** Hane は Unicode 入力の LF も CR も改行として扱わず（改行には本物の Enter キーが必要）、複数行のテキストは 1 行に連結される。方針（Enter を送らない）は守っているが、整文の結果に段落がある場合に影響する。選択肢: (a) このまま（単一行の発話が主なら実害は小さい）、(b) アプリ別に「改行を Enter キーで送る」を明示的に選べるようにする（Enter が確定・送信になるアプリでは選ばない、という利用者の責任）、(c) 改行を空白に置き換える。推奨は (a) を既定とし、必要が出たら (b) を足すこと。
2. **メモ帳の新規タブ直後は、素の入力の最初の 2 キーイベントが落ちる**（§3.4）。メモ帳は auto（paste-message）で足りるので上書きしない想定だが、`typing` / キー系をメモ帳に指定すると最初の数文字が落ちる可能性がある。落ちる原因（メモ帳の入力サイトの初期化か、リマッパか）は切り分けていない。
3. **前面化は、直接の `SetForegroundWindow` が拒否される場面が普通にある**（ログが残っている 3 回は 3 / 3 で拒否され、スレッド入力への接続で成功）。前面化に失敗したときに何も送らない経路は、実機で再現できなかったため、実測していない（コード上の分岐のみ）。管理者権限で動くウィンドウ（UIPI）、前面化を禁じる設定、日本語 IME が有効なときの typing は未検証。前面化したあと元の前景ウィンドウへは戻さない（記録先が前面に残る）。
4. **キー系の経路（ctrl-v / shift-insert / custom）の他アプリでの成否は未測定。** 検証環境のリマッパが Ctrl+V をスクロールに割り当てているため、この環境では Hane・メモ帳とも貼り付けにならない（M9 で確認済み）。リマッパの無い環境や、custom で貼り付けに別のキー（リマッパが再定義していないもの）を割り当てる場合の成否は、利用者の環境で確認が要る。
5. 旧 `insertion.method`（clipboard / sendinput）は保存値として維持したが、どの経路にも使われない（M9 以前から未使用）。設定画面の無効なラジオは外した。値を消すか使うかは今後の判断。
6. typing は長文を 256 コード単位ずつ送る。入力の途中で前面が変わると中断し、そこまでの文字は入ったままテキストは Failed として保持される（再試行すると、入った分と重複する）。長文の速度は実測していない（数千文字でも 20 回前後の `SendInput` で済む設計）。
7. 実測の環境: 計測中に前景を切り替える操作（Alt キー押下を伴う）を使ったため、フォーカス状態は実利用と完全には一致しない。メモ帳のタブ・一時ファイル、起動した Hane は閉じていない。誤って起動した製品本体のプロセス（診断の引数の渡し間違い）は終了させた。
8. 単体テストの限界: 前面化（`BringToForeground`）と `SendInput` の実送信は、非対話セッションでは検証できないため単体テストの対象外で、§3 の実測で確認した。
