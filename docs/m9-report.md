# M9 レポート: 投入経路の振り分けとクラウド文字起こしの言語指定

利用者の実地報告（v0.3.0-preview.1）に基づく 2 件の修正。(1) 処理後テキストの投入成功率の改善、(2) クラウド文字起こしの言語指定。

## 1. 実地報告

- 投入の成功率が低い。最も良いメモ帳でも半分程度で、「一度成功すると次からは比較的うまく行く」。他のアプリはかなり失敗する。
- GPUI のカスタム描画 UI を使うエディタ（Hane）では一度も成功しない。
- LiteLLM 経由の文字起こしが、日本語以外の言語として認識されることが多い。

## 2. 修正 1: 投入経路

### 2.1 実測（修正前、v0.3.0-preview.1 相当の経路ロジック）

検証用 Windows（ARM64、キーリマッパ常駐のまま・停止なし）の対話セッションで、`--inject-probe` を状態ごとに 10 回ずつ実行した。診断を拡張し、前景プロセス・前景クラス・`GetGUIThreadInfo` の `hwndFocus` のクラス・宛先クラスを probe に出すようにした（タイトルは出さない）。成否は probe の `result=` ではなく、対象側の実内容で判定した（メモ帳は UI オートメーションで文書内の投入文字列の増分、Hane は文書領域の画面差分と目視）。Hane は GitHub Releases の最新版 Windows ビルド（x64 zip、ARM64 上のエミュレーション実行）を、更新状態に影響しない別フォルダー・別の状態保存先で起動した。

| 対象・状態 | probe の報告 | 実際に貼り付いた | focus のクラス |
|---|---|---|---|
| メモ帳: 新規ウィンドウ直後 | 10/10 Success | **0/10** | 常に `InputSiteWindowClass` |
| メモ帳: 同じウィンドウで連続 | 10/10 Success | **5/10** | `InputSiteWindowClass` と `RichEditD2DPT` が交互 |
| メモ帳: 他アプリへ移した後に戻す | 10/10 Success | **6/10** | 前半 `RichEditD2DPT`、後半 `InputSiteWindowClass` |
| Hane: 編集領域を押した後 | 10/10 Success | **0/10** | `Zed::Window`（最上位ウィンドウ自体） |
| Hane: フォーカスを移しただけ | 10/10 Success | **0/10** | `Zed::Window` |

分かったこと:

- **Hane**: フォーカス中の宛先は最上位の `Zed::Window` で、`WM_PASTE` は「届いた」扱い（`Delivered`）になるが無視され、予備経路（SendInput）へ落ちない。想定どおり。
- **メモ帳（新しい WinUI 版）**: Win32 のフォーカスが、内側の編集コントロール（`RichEditD2DPT`）ではなく XAML アイランドの入力サイト（`InputSiteWindowClass`）に見える状態があり、このとき `WM_PASTE` は同様に無視される。新規ウィンドウ直後は常にこの状態、その後は編集領域へフォーカスが入るまで交互に現れる。「初回だけ失敗し、一度うまくいくと次から比較的うまく行く」はこれで説明できる（M8 の実測で `RichEditD2DPT` が宛先だったのは、編集コントロールにフォーカスが入っていた状態）。
- いずれも probe は常に Success を返す。Delivered は「メッセージが戻った」だけで、貼り付けの成否ではない。

### 2.2 変更

`TextInjector` の貼り付け段（`PasteToForeground`）を、フォーカス中コントロールのクラスで振り分けるようにした。

- 宛先は投入の直前（クリップボードへ設定した後）に解決する。解決した前景が自プロセス・シェル・デスクトップなら何も送らず「入力先のウィンドウが見つかりません」で失敗し、クリップボードは復元する（待ちなし）。宛先が全く得られないときは従来どおり SendInput へ落ちる。
- `Classify`: クラスが `Edit` / `RichEdit*`（`RichEditD2DPT` を含む）/ `Scintilla` なら標準の編集コントロール、それ以外はカスタム描画。標準クラスで実測確認したのは Edit 系と RichEdit 系。Scintilla は `WM_PASTE` を実装する代表的な編集コントロールとして加えたが、実測はしていない。
- Auto の経路: 標準クラスは `WM_PASTE`（宛先なし・失敗・時間切れなら従来どおり SendInput へ落ちる）、カスタム描画は SendInput（Ctrl+V）のみ。強制指定（`--strategy`）はクラスを無視する。
- **メモ帳の追加対応（実測に基づく、指示にない拡張）**: フォーカスが `InputSiteWindowClass` のときは、前景ウィンドウ内で**可視の標準編集コントロールがちょうど 1 つ**ならそれを `WM_PASTE` の宛先にする（`hosted_editor=True`）。0 個・複数個なら曖昧なのでカスタム描画として SendInput へ回す。この対応を入れず指示どおりの振り分けだけにすると、メモ帳は `InputSiteWindowClass` を「カスタム描画」と判定して SendInput になる。検証環境のキーリマッパは Ctrl+V を貼り付けではなくスクロールに割り当てており、SendInput を強制した実測ではメモ帳が **0/20** だった（新規直後 10 回・連続 10 回とも貼り付かず）。振り分けだけでは成功率が下がるため、この対応を入れた。
- `InjectResult` に `TargetClass`（宛先クラス）を追加（既存の `Route` と併せて、使った経路と宛先クラスが残る）。probe は `target ...`（前景クラス・focus・宛先クラス・`hosted_editor`・`kind`）、`route_by_class=send-input`（振り分けで SendInput にした場合）、`route_used`、`target_class_used` を出す。

### 2.3 検証（修正後、同じ手順）

publish した exe（`-Version 0.3.0-preview.2`、ARM64）で、状態ごとに 10 回ずつ、キーリマッパ ON のまま。

| 対象・状態 | 経路 | 実際に貼り付いた |
|---|---|---|
| メモ帳: 新規ウィンドウ直後 | paste-message（`InputSiteWindowClass` → `RichEditD2DPT` に解決） | **10/10** |
| メモ帳: 同じウィンドウで連続 | 同上 | **10/10** |
| メモ帳: 他アプリへ移した後に戻す | 同上 | **10/10** |
| Hane: 編集領域を押した後 | send-input（`route_by_class`、カスタム描画） | **0/10** |
| Hane: フォーカスを移しただけ | send-input | **0/10** |

メモ帳は修正前 11/30 から **30/30**（二重貼り付けなし、増分は常に 1）。

**Hane はこの環境では解消していない（0/20）。** 経路は意図どおり SendInput（Ctrl+V）になったが、検証環境に常駐するキーリマッパ（Emacs 風）が Ctrl+V を貼り付けではなく「ページ送り」に割り当てており（その設定の `scroll_key` に `C-v` があり、Hane は除外対象に入っていない）、キーが貼り付けとして届かない。同じ環境で次を比較した（Hane、画面で確認）:

| 送ったもの | Hane の文書への反映 |
|---|---|
| SendInput の Ctrl+V | 変化なし |
| SendInput の Shift+Insert（クリップボードに文字列を置いた状態） | 変化なし |
| SendInput の Unicode 文字入力（`KEYEVENTF_UNICODE`） | **入る**（文字数 +17、日本語を含む） |

つまり Hane には「クリップボード経由の貼り付け」がこの環境ではどの手段でも届かず、キーリマッパを通らない文字入力だけが届く。これは本タスクの範囲（Ctrl+V を主経路にする）を超えるため実装していない。**判断が必要**（§4）。keyhac の設定とスクリプトは変更しておらず、OFF にもしていない。

## 3. 修正 2: クラウド文字起こしの言語指定

- 設定キー `recognition.cloud.language`（既存の `base_url` / `api_key_dpapi` / `model` と同じ snake_case、クラウド設定の入れ子）。既定は `ja`。空文字列は「指定しない」。
- 既定（`ja`）のときは設定ファイルへ書き出さない（既存の「追加キーは既定のとき書かない」方針）。空は「自動判定」を表すので明示的に書き出す。旧版が書いた設定は `ja` として読める。
- `CloudTranscriber` の multipart は、言語が空でないときだけ `language` フィールドを追加する（`Content-Type` なし、値は入力のまま）。空なら `file` と `model` の 2 つのままで、`language` フィールド自体を送らない。
- 言語コードの検証（`CloudRecognitionConfig`）: 空、または英数字とハイフンだけの 16 文字以内。不正なら準備不能（「クラウド認識の言語コードが不正です」）で、ネットワークを呼ばない。
- 診断の `--transcription-probe` と、`--pipeline-file --use-settings` は製品と同じ構えを通るので同じ指定が効く。E2E の multipart 検査は `file,model,language` に更新した。
- 設定画面のクラウド欄に「言語コード」の小さい入力欄（既定 `ja`、空欄で自動判定、説明文つき）。接続設定の消去で `ja` に戻る。
- 設計書（`design-cloud-transcription.md`）の「language は送らない」の記述を、M9 での変更として更新した。

## 4. 判断が必要な点・未検証・限界

1. **Hane（カスタム描画）への投入**: キーリマッパが Ctrl+V を再定義している環境では、SendInput（Ctrl+V）も Shift+Insert も届かない。確認できた唯一の手段は Unicode 文字入力（SendInput の `KEYEVENTF_UNICODE`）。カスタム描画クラスの第 2 の予備経路・既定経路として入れる場合の論点: 改行文字の扱い（Enter として送られるアプリでは確定・送信になりうる）、日本語 IME 有効時の挙動、長文の速度、クリップボードを使わないため退避・復元が不要になること。実装するかの方針を決めてほしい。リマッパが Ctrl+V を再定義していない環境では、今回の変更だけで Hane に貼り付く見込みだが、この環境では確認できていない。
2. **probe の Success は貼り付けの成否ではない**: SendInput は「送信できた」、WM_PASTE は「メッセージが戻った」までしか分からない。対象側の内容で確認する必要がある（本レポートの実測もそうした）。
3. **未実測のアプリ**: ブラウザ、Electron、Office、WinForms / WPF の編集コントロール、Windows Terminal など。これらは今回の分類ではカスタム描画（SendInput）になる。WinForms の編集コントロールは `WindowsForms10.EDIT...` のような別クラス名なので標準扱いにならず、SendInput へ回る。WPF の TextBox も同様。いずれもリマッパが Ctrl+V を再定義していなければ貼り付く想定だが、実測していない。
4. **メモ帳の宛先解決の前提**: 可視の標準編集コントロールがちょうど 1 つ、という前提。分割表示など編集領域が複数見えるアプリでは曖昧として SendInput へ回る。
5. Hane は x64 ビルドを ARM64 上のエミュレーションで実行した。Hane の更新機構は、展開直後の場所では中断された更新の記録を理由に起動を止めたため、別フォルダー・別の状態保存先で起動した（Hane 側の既定の保存先・設定には触れていない）。
6. 計測時の注意: 対話セッションのタスクから前景を切り替える操作（Alt キー押下を伴う）を使ったため、メモ帳のフォーカス状態は実利用と完全には一致しない。ただし、状態ごとの傾向（新規直後は入力サイト、連続時は交互）は修正前後で同じ手順なので比較は成立している。
7. 計測に使ったメモ帳の一時ファイルのタブ（空のファイル）は閉じていない。

## 5. テスト（Windows ARM64、`dotnet test` 全件）

修正前 685 件 → **717 件合格、失敗 0、スキップ 0**（新規 32 件）。

- 経路振り分け: `Classify`（標準クラス 5 種、カスタム 6 種）、Auto + カスタム = キーのみ（メッセージを送らない）、Auto + 標準・宛先未解決 = メッセージ優先、標準で失敗したら SendInput へ落ちる、強制指定はクラスを無視する。
- 入力サイト解決: 可視の標準編集コントロールが 1 つだけならそれを返す（非表示の親の下のものは無視）、なし・複数は null。実際のウィンドウ木で検証（非対話セッションでは `IsWindowVisible` が `WS_VISIBLE` のウィンドウでも偽を返すため、試験は `WS_VISIBLE` を祖先までたどる可視判定を注入する）。
- 言語: multipart に既定の `ja`・指定コード（`en` / `zh-CN`）が入り、空では `language` が入らない、設定の既定は書き出さず空と `en` は往復する、検証（正常 3 / 不正 4）、`Ready` への伝播と不正値での準備不能。既存テスト 1 件（multipart の構成）は language を含む 3 部構成に更新。
- E2E（`build/cloud-transcription-e2e.ps1 -SkipLong`、ループバックのモック、ARM64）: 53 件すべて合格。
