## 1. T11 の完了条件への対応

完了条件（設計タスク表）: 接続成功、エラー・停止・空・期限で原文を一度投入。固定指示と adversarial 入力試験、キー非出力を確認。

| 単位 | 役割 |

| `Core/SessionCoordinator.cs` | `Polishing` 状態を追加（§3.3）。整文の構えは**録音開始時に固定**（設計 §3.2）。原文を保持し、整文の完了・失敗・期限・取消をセッション ID 付きイベントで直列処理 |

### 条件ごとの結果

| 条件 | 結果 | 根拠 |
| --- | --- | --- |
| 接続成功 → 整文結果を投入 | **実測** | 単体（ループバック実 HTTP）と E2E（実 exe ↔ モック）。整文結果だけが一度投入され、原文は投入されない。状態は Recording → Recognizing → **Polishing** → Inserting → Idle |
| リクエスト形式 | **実測** | `model` / `messages`（system = 固定指示、user = 認識テキストをそのまま）/ `stream:false` の 3 キーだけ。`temperature` 等は送らない。`Authorization: Bearer` はキーがあるときだけ。パスは `/v1/chat/completions`（末尾 `/` や `/v1` の有無でも `/v1` を消さない 6 パターンを確認）。リクエスト本文は JSON のため日本語は `\uXXXX` にエスケープされて送られる（有効な JSON） |
| 応答解析 | **実測** | `choices[0].message.content` の文字列と `finish_reason == "stop"` を確認。先頭の候補だけを使い、複数候補は連結しない。前後の空白は除去 |
| 受信上限 1 MiB | **実測** | 宣言サイズ超過は読まずに `TooLarge`、1 MiB 直前は成功 |

### フォールバック（原文をちょうど一度だけ投入）

単体テスト（Coordinator 側は全失敗分類、クライアント側は 25 種の不正応答）と、E2E（実 exe ↔ モック。投入が 1 回・原文と一致・モックへの要求が 1 回だけ＝自動リトライなし、を各ケースで確認）の両方で確認した。

| ケース | 結果 | 検証経路 |
| --- | --- | --- |
| HTTP 500 / 404 / 429 | 原文を 1 回（`Http`、補足は「HTTP n」のみ） | 単体 + E2E(500) |
| HTTP 401 / 403（認証失敗） | 原文を 1 回（`Auth`） | 単体 + E2E(401) |
| 応答本文にキーと要求を埋め込む 401 | 原文を 1 回。**出力・結果に本文もキーも出ない** | 単体 + E2E(echo401) |
| `content` が空 / 空白だけ / null / 欠落 | 原文を 1 回（`Empty`） | 単体 + E2E(empty, blank, nocontent) |
| JSON でない / 配列 / `choices` なし・空 / `message` なし / `content` が配列・数値 | 原文を 1 回（`Malformed`） | 単体 + E2E(malformed) |
| `finish_reason` が `length` / `content_filter` / null / 欠落 | 原文を 1 回（`Incomplete`） | 単体 + E2E(length, notstop) |
| `tool_calls` / `function_call` を含む応答 | 原文を 1 回（`Malformed`） | 単体 + E2E(toolcalls) |
| 1 MiB 超の応答 | 原文を 1 回（`TooLarge`） | 単体 |
| 3xx リダイレクト | 追わない。**転送先への要求 0 件**（キーも本文も届かない）。原文を 1 回 | 単体 + E2E(redirect) |
| 接続拒否 | 原文を 1 回（`Network`、補足なし） | 単体 + E2E |
| 応答が返らない（停止） | **期限（15 秒）で原文を 1 回**。実測 ARM64 15.04 s / x64 15.12 s（認識完了から投入完了まで）。期限後に遅れて届いた応答は捨て、二重投入しない | 単体（短い期限）+ E2E（実 15 秒） |
| ヘッダー受信後に本文が止まる | 期限で原文を 1 回（`Timeout`） | 単体 |
| 不正なプロキシ設定 | **直結へ逃げず**原文を 1 回（`Network`）。サーバーへの要求 0 件 | 単体 |
| キーに制御文字（ヘッダー注入の試み） | 送信せず原文を 1 回 | 単体 |
| 整文側の実装が例外 / 取消を無視して戻らない | 原文を 1 回（例外は `Error`、戻らない場合は Coordinator 側の期限） | 単体 |
| 成功だが空白だけの本文 | Coordinator が信用せず原文を 1 回 | 単体 |
| 整文の投入が失敗（投入先不適切など） | 整文済みの一件を保持し、トレイの再試行で同じ一件を投入（M1 の挙動を踏襲） | 単体 |

失敗時は控えめな通知（トレイのバルーン。種類 `Warning`）で「整文できなかったため、そのまま入力しました（理由の短い分類）」を出す。分類は固定の短い文言で、応答本文・URL・例外メッセージは含めない。

### 利用者の取消（整文中）

設計に明記があった: §3.3「認識 / 整文 — ピルのキャンセル — トークン取消 … キャンセル → 待機」、§7.1「ユーザーキャンセルと失敗を区別し、**キャンセル時に原文を勝手に貼り付けない**」。したがって**取消は何も投入しない**（M1 の取消と一致）。実装: トークンを取消し、原文を破棄し、セッション ID を進めて待機へ。遅れて届いた整文結果は ID の不一致で捨てる（単体テストで、取消後に遅れて完了させても投入 0・状態不変・通知なしを確認。取消直後の新セッションが古い完了に影響されないことも確認）。整文中のホットキー再押下は新しい録音を始めない（確認済み）。

### adversarial 入力

認識テキストは「データ」として扱う。固定指示とは別メッセージ（system / user）で、テキストを指示文へ文字列結合しない。

| 確認内容 | 結果 |
| --- | --- |
| 10 種の入力（「以前の指示を無視して…」、英語の指示、JSON を壊して `role:system` を注入しようとする文字列、`### system` の偽見出し、コードフェンス、チャットテンプレートのトークン、エスケープ文字・`"model":"gpt-evil"` を含む文字列、サロゲートペア・双方向制御文字、制御文字混在、5 万字）で、リクエストが**常に** `model` / `messages` / `stream` の 3 キー、メッセージ 2 件（system → user）、system の内容は**固定指示とバイト一致**、user の内容は**入力と一字一句一致**、`model` / `stream` が上書きされない | **実測**（単体、実 HTTP） |
| 発話が普通の文でも injection でも system メッセージが同一 | **実測**（単体） |
| E2E（実 exe）でも、injection を含む認識テキストを送り、system に「ハッキング成功」が入らず、user が原文そのまま | **実測** |
| 実際の Whisper 認識結果（ARM64、small）がそのまま user メッセージとして送られ、モックの整文結果が投入される／500 のときは認識結果そのものが投入される | **実測**（ARM64。x64 は認識まで通していない） |
| **実際の LLM が発話中の指示に従わないか** | **未確認 / コードでは保証できない**。クライアントができるのは構造の分離と、応答を「本文」としてだけ扱うこと（ツール呼出し・別フィールドは成功扱いしない）まで。モデルが指示に従った応答を返した場合は、その文字列が整文結果として投入される（単体テストで、そうした応答が本文として素通りすることを明示的に確認＝検出はしない）。品質の評価は設計 §12.1 のとおり人手 |

### 未設定時の表示

`provider=compatible` で整文できない状態は、整文を試みず原文を投入し、トレイのバルーンで「整文の設定が未完了のため、そのまま入力します（理由）」と知らせる（ピル・トレイの最小限の表示）。

| 状態 | 結果 |
| --- | --- |
| ベース URL 未設定 / 不正、モデル名未設定 | `Unconfigured`（単体）。**ただし実際の config.json ではこの状態を作れない**: 設定の検証（M2）が、compatible で URL・モデルが空・不正な設定の保存と読み込みを拒否するため（設定ウィンドウは保存を拒否、手編集は「設定エラー」で整文以前にホットキーも無効）。E2E では扱わず、単体テストだけで確認 |
| 外部（非 loopback）の送信先で API キー未設定 | `Unconfigured`。**実 exe で確認**（試行なし、原文 1 回、通知あり、`Polishing` に入らない） |
| キーを復号できない | `Unconfigured`（単体） |
| `provider=chatgpt`（未実装） | 送信せず原文 1 回、通知あり。設定値は変えない（実 exe で確認）。設定ウィンドウでは引き続き選べない |

## 2. ホットキー永続化の修正

### 仕様（司令塔決定）と実装

- **交渉結果（採用キー）は `config.json` に保存しない。** `config.json` の `hotkey` を書くのは、設定ウィンドウで利用者が明示的に選んで保存したときだけ。
- 起動時の交渉順は「設定のキー → 設計の既定候補順（重複は除く）」（`HotkeyNegotiator.CandidatesFor`。M2 から変わらず、`SettingsHotkeyStore.NegotiationOrder()` がそれを返す）。
- `IAdoptedHotkeyStore`（M1 の暫定境界）を**廃止**した。`SettingsHotkeyStore` は交渉順を返すだけで、書き込みの経路を持たない。
- 診断出力は `hotkey_adopted=` のみ。**`hotkey_persisted=` は廃止**した（明示保存だけが永続化の経路なので、起動時に出す意味がない）。
- 設定ウィンドウの副次修正: ホットキーを変更して保存し、その後の段階（自動起動・保存）で失敗した際の巻き戻し先を、「設定のキー」から「直前に実際に有効だった採用済みのキー」へ変えた（採用結果を保存しなくなったことで、両者が異なり得るため）。

### テストで固定した内容（`HotkeyPersistenceTests` ほか）

| 要件 | 結果 |
| --- | --- |
| (a) 初回起動で Win+J が取れず Ctrl+Win+J が採用されても `config.json` は作られない（ディレクトリが空のまま）。既存の `config.json` はバイト一致のまま。全滅でも書かない。読み込み失敗中の `config.json` も無変更 | **実測**（単体） |
| (b) 設定で明示的に保存したキーは保存され、次回その先頭に既定候補が続く（重複なし）。保存したキーが先頭で試され、取れればそれが採用される | **実測**（単体 + 設定ウィンドウの診断。ARM64 / x64 で、ウィンドウの保存後に再読み込みした交渉順が `Ctrl+Alt+K,Win+J,Ctrl+Win+J,Ctrl+Alt+J`） |
| (c) 一時失敗（Win+J のみ失敗 → Ctrl+Win+J 採用）の次回起動では、再び Win+J が先頭で試される | **実測**（単体） |
| 採用キーがあるまま無関係な設定（モデル）を保存しても、保存されるのは設定のキー（Win+J）で、採用キーが混入しない | **実測**（単体） |
| 実 exe の常駐起動（クリーンなディレクトリ）で、`hotkey_adopted=` が出て `hotkey_persisted` が出ず、`config.json` が作られない | **実測**（ARM64 / x64。ただしセッション 0 では 3 候補すべて Win32 エラー 1459 で失敗するため、「一部だけ失敗」の経路は単体テストでのみ確認） |

利用者向けの挙動: Win+J が一時的に占有されて Ctrl+Win+J が採用された場合、トレイの tooltip に採用キーが出る。設定ウィンドウには「設定のキー」（Win+J）が出る。次の起動で Win+J が再び試される。設定ウィンドウで保存するとき、ホットキーを変更しない限り再登録は試みない（占有が解けても、再起動するかキーを一度変えるまで採用キーのまま）。

## 3. 設計・依頼からの逸脱と判断

| 点 | 内容と理由 |
| --- | --- |
| 互換エンドポイントでの API キー | 依頼は「base_url / API キー / モデル名のいずれかが未設定なら整文しない」、設計 §7.2 は「認証不要のローカルサーバーでは空キーを許す」。両立させるため、**キー未設定は外部の送信先でだけ「未設定」扱い**とし、loopback（`localhost` / `127.0.0.1` / `::1` と `*.localhost`）はキー無しで許す。外部へキー無しで送る構成は作らない |
| `finish_reason` の扱い | 「正常な終了」の確認として `"stop"` 以外（null・欠落を含む）を未完了として原文へ戻す。`finish_reason` を返さない互換サーバーでは常に原文になる可能性がある。実エンドポイント確認で問題が出たら緩める判断が要る |
| 整文の構えを録音開始時に確定 | 設計 §3.2（設定変更は次のセッションから）に従った。compatible のときは録音開始のたびに DPAPI を復号する（キーはそのセッションの間だけメモリに保持） |
| Coordinator 側の期限 | 整文実装が自前の期限（クライアントの 15 秒）を守らなくても原文へ戻れるよう、同じ期限の保険を Coordinator にも置いた |
| 通知の種類 `Warning` を追加 | 整文できなかった通知を、エラー（Error）と区別するため。表示はトレイのバルーン |
| 整文失敗のピル表示 | §6.1 の琥珀色の点と「整文できなかったため、そのまま入力」（最長 3 秒）はピルに実装していない（T14）。代わりにトレイのバルーンで知らせる。ピルには「整文中」の表示（取消可）だけ追加 |
| 設定ウィンドウの文言 | 「保存のみ（T11 で有効）」の注記を、実際の動作（互換エンドポイントを選ぶと認識テキストだけを送る・失敗時は原文・ChatGPT は未対応）に更新 |
| `hotkey_persisted=` の廃止 | §2 のとおり。明示保存時にだけ意味を持たせる案は採らなかった |
| 診断モードの追加 | `--cleanup-probe` / `--write-cleanup-config`（実 exe で整文経路を非対話に確認するため）、`--pipeline-file --use-settings` に整文の結線と `--config` を追加。M1/M2 と同じ扱い（T17 で見直す） |
| モックサーバーの置き場所 | `build/mock-compat-server.ps1`（PowerShell の `HttpListener`）。製品には含めない。E2E スクリプトは `build/m3-cleanup-e2e.ps1`、ホットキーの常駐起動確認は `build/m3-hotkey-startup-check.ps1`。PowerShell 5.1 が BOM なし UTF-8 を誤読するため、日本語を含むスクリプトは BOM 付き UTF-8 |

## 4. ビルド・実行手順（追加分）

```powershell

build\publish.ps1 -Arch all -Out <dir>                            # M1 と同じ
build\m3-cleanup-e2e.ps1 -Exe <dir>\win-arm64\whisparrot.exe [-Wav <wav>]   # モックとの E2E（-Wav で実認識込み。models\ を exe の隣へ）
```
