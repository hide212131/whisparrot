## 実装範囲と設計書の対応

### S-1 連続 PCM・有界バッファ・固定秒数分割・末尾回収（§1・§2・§3・§7）

| 設計 | 実装 |
| --- | --- |
| §1 連続 PCM フレームを受ける録音インターフェース | `Core/Streaming/Streaming.cs` の `IStreamingRecorder`（`StartStreaming()` が 16 kHz mono の `PcmFrame` を返す `ChannelReader`、`StopStreamingAsync()`、`DroppedSamples`）。`IRecorder` を継承するので `Cancel` / `Failed` は従来どおり。マイクは区間ごとに開閉しない |
| §1 OnData から有界バッファ、単一の変換でリサンプラー状態を維持 | `WasapiRecorder` が `IStreamingRecorder` を実装。`OnData` → `StreamingResampler`（一つの `WdlResamplingSampleProvider` を録音の間じゅう維持）→ `FrameBuffer` |
| §3・§7 キャプチャ側のリングは最大 2 秒、満杯なら受け入れを省いて数える | `Infrastructure/Audio/FrameBuffer.cs`。上限は**サンプル数**（2 秒 = 32,000）で、コールバックを待たせない。省いた分もサンプル位置は進めるので、読み手は `StartSample` の不連続から欠けを検出する |
| §2 固定秒数分割、16 kHz のサンプル位置基準 | `SegmentSplitter`（`Push` / `Flush`）。目標長ちょうどで確定、連番は 1 から連続、フレームの大きさに結果が依存しない。欠け（ギャップ）では手前までを一区間にして、欠けをまたいで連結しない。既に取り込んだ位置との重なりは捨てる |
| §2 停止時の末尾は最小長未満でも処理 | `Flush()` が末尾を一度だけ確定（空なら何も出さない。以後の `Push` は無視 = 終端の一意性） |
| §5 停止の余韻回収（250 ms） | `StopStreamingAsync` が既存の `TailGrace` を使う。どの終了経路でもチャンネルを完了してデバイスを解放する |
| §7 録音は 1 回 20 分まで | 区間の読み手が録音位置を見て上限で自動停止し、通知してフラッシュ |
| 一括録音の互換 | `Start()` / `StopAsync()` / `Cancel()` は従来の実装のまま（実機で `--record-probe` が従来どおり動くことを確認） |

`Core/SessionCoordinator.Streaming.cs`（`partial`）。既存の単一イベントループに、区間番号付きの完了イベントを足した。

| 設計 | 実装（数値は設計どおり。`StreamingLimits` の既定値） |
| --- | --- |
| §3 `(sessionId, sequence)`、終端済み区間の遅い完了は破棄 | 完了イベントは `(Id, Seq)` 付き。別セッション・終端済みの区間のイベントは捨てる |

| §3 期限: 認識 24 秒 | 区間確定から 24 秒で取消・欠落 |
| §3 期限: 整文は開始から 15 秒かつ区間確定から 32 秒、枠待ちを含む | `min(開始+Timeout, 確定+32秒)`。超えたら原文を出力候補にする（整文 OFF・失敗・空も原文） |
| §3 期限: 出力枠待ちは 40 秒 | 未送出の区間を欠落にする |
| §3 期限と枠の分離 | 期限で結果を確定しても、認識・整文の実行枠は**呼び出しが実際に終わるまで**返さない（完了イベントで解放）。取消を無視する認識が居座ると後続は始まらない（テストで確認） |
| §5 停止: 新規取り込み終了 → 末尾を一度だけ確定 → 残りを流す | `Recording → Flushing`（新状態）。新規録音はフラッシュ完了後 |
| §5 フラッシュ期限 25 秒、その後 5 秒の送出枠 | 25 秒で未完了の認識を欠落、整文中は原文へ。さらに 5 秒で未送出を欠落にする。送出中の一件は完了を待つ |
| §5 取消 | 取り込み停止、実行中の認識・整文・未送出を破棄、投入には取消トークン。通知は「取消しました。入力済みの内容は残ります」（送出中なら「送信済みの入力は反映される場合があります」を添える） |
| §6 失敗しても継続 | 認識失敗・期限切れ=欠落、整文失敗=原文、空の認識結果は欠落と別に「空」で数える |
| §6 集約通知、連続 3 区間の警告 | 完了時に「入力 N 区間・原文のまま M 区間・欠落 K 区間」（空・適用未確認・取消があれば追記）。原文のまま/欠落が連続 3 区間で、セッションにつき各一度だけ警告 |
| §6 マイク切断 | 回収できた区間と確定済みの区間をフラッシュ |
| §6 入力先変更・適用不明 | 以降の自動投入を止め、録音・認識・整文と未出力を打ち切り、直近一件を既存の `HeldText`（新種別 `StreamingNotInjected`）に保持。トレイの「入力できなかった区間をコピー」で取り出せる |
| 汎用経路の投入順（判断 2） | 整文の完了を待って、連番順に投入（原文先行はしない）。整文 OFF なら認識原文 |
| §4.2 区間境界の空白 | `SegmentJoin.Separator`: ASCII の英数字どうしの境界にだけ半角空白を 1 個。日本語の境界はそのまま、改行は足さない |

## 追加テスト（74 件、`StreamingSplitterTests` / `StreamingSessionTests`）

- **区間の切り分け**: 目標長で確定・連番 1 から、フレームの大きさ（1〜128,000 サンプル）に依存しない・取りこぼしと重複がない、末尾は最小長未満でも一度だけ、無音の空録音、ギャップで区間を閉じる、重なりフレームの切り詰め、隣接区間の終端 = 次の始点、不正な目標長。
- **有界バッファ**: 満杯での受け入れ省略と欠落数・位置の一意性、欠けがスプリッターにギャップとして見える、上限がフレーム数でなくサンプル数、`ReadAllAsync` で読み切れる。
- **連続リサンプラー**: 16 kHz は素通し、48 kHz / 44.1 kHz をフレーム分割して流しても連続した正弦波（クリックなし・振幅一定）。
- **連番と順序のそろえ方**: 録音中に複数回入る・停止で末尾が入る、認識の完了順を逆転させても追い越さない、整文の完了順を逆転させても追い越さず整文後の本文を使う、認識の同時 2 件・整文の同時 2 件、投入は一件ずつ、英数字境界の空白。
- **期限切れ区間の扱い**: 認識期限で欠落・期限後の遅い成功は無視、呼び出しが終わるまで枠を返さない、整文の時間切れ・失敗・空は原文、出力枠待ちの打ち切り、フラッシュ期限で未認識を欠落・整文中は原文、送出枠を過ぎた未送出の欠落。
- **停止時のフラッシュ**: 逆順完了でも連番順、音声なし、フラッシュ中の新規録音は無視、録音上限での自動停止、マイク切断でのフラッシュ。
- **取消**: 取消後に何も入らない（遅い完了も）、投入中の取消で後続は入らず注意文を出す・取消トークンが渡る、フラッシュ中の取消。
- **区間失敗時の継続**: 認識失敗・空の結果（別集計）・連続 3 区間の警告は一度だけ、投入失敗で自動投入を止めて直近一件を保持・適用不明は別集計、飽和（上限超えは欠落で連番順は保つ）。
- **設定 OFF 時の不変性**: OFF のとき一括経路のまま（状態遷移 `Recording → Recognizing → Inserting → Idle`、`InjectSegmentAsync` 不使用）、設定の供給元なし、連続録音に対応しない録音は一括、ローカル認識は一括 + 通知、入力先なしは録音を始めない。
- **設定**: 既定 OFF・8 秒、既定は書き出さず既存設定を読める、往復、4〜20 の整数だけ有効、非整数・未知キーの拒否。
- **厳密確認**: `StrictMismatch` の判定表（前景・PID・フォーカス・宛先の消失、XAML アイランドの許容）、入力先なしの失敗。
- 既存の `AudioTests` / `CloudPipelineTests` / `SessionCoordinatorTests` / `InsertionRouteTests` を含む 1030 件は変更なしで合格。

## 実地確認（Windows 検証機）

### 確認した範囲

標準音声 `part1.wav` + `part2.wav`（計 130.9 秒、16 kHz mono）を連続録音として流す診断 `--streaming-probe`（新規）。**本物の**コーディネーター・`SegmentSplitter`・`SettingsRecognizer` → `CloudTranscriber`（WAV 化・HTTP・NetworkContext）を通し、認識先だけはこのコマンドが 127.0.0.1 に起こす擬似サーバー（受け取った WAV が元音声のどの区間かを照合して識別子を返す）。投入先は記録するだけの代役。区間 8 秒（既定）。

| 条件 | 結果 |
| --- | --- |
| 4 倍速、奇数番の応答を 3 秒遅らせて完了順を逆転、整文モックも区間 1 だけ遅延 | 17 区間（8 秒 × 16 + 末尾 2.9 秒）が**連番どおり**に入った（`order_ok=True`）。区間 2 の応答が区間 1 より先でも、区間 1 の後に入った。認識の同時要求は最大 2。録音中（停止前）に 14 回入り、**停止後に残り 3 回**が流れて `Flushing` → `Idle`。通知は「入力 17 区間・原文のまま 0 区間・欠落 0 区間」 |
| 等速（130.9 秒）、奇数番を 1.5 秒遅延、整文モック付き | 17 区間が連番どおり。録音中に 16 回（8 秒間隔の周期で入力）、停止（130.9 秒）の 1.6 秒後に末尾の区間が入って終了。同時要求は最大 1（遅延が間隔より短いため） |
| 20 秒で停止（4 倍速） | 区間 1・2 が録音中に入り、停止直後に末尾区間 3 が入って Idle（計 3 区間、順序 OK） |
| 20 秒で取消（4 倍速、応答遅延あり） | 取消後の入力は 0、Idle へ戻り「取消しました。入力済みの内容は残ります」。取消後に届く応答は入力されない |
| 区間 2 の応答を返さない（4 倍速、part1 のみ） | 区間 2 は実時計の 24 秒で期限切れ=欠落。後続の区間 3〜9 は区間 2 が確定するまで待ってから連番順に入り、通知は「入力 8 区間・原文のまま 0 区間・欠落 1 区間」。**1 区間の停滞で後続の出力が最大 24 秒遅れる**ことを実測（設計どおりの挙動） |
| 実マイクの連続取り込み（`--record-probe 3000 --streaming`） | `WasapiRecorder.StartStreaming` で 3 秒録音 + 余韻、フレーム 51 個・計 3.1 秒、**フレームの欠け 0**・省略 0、停止後にチャンネルが完了。取消でも完了し、一括の `--record-probe` も従来どおり動作（無音または環境音のみ。発話での確認ではない） |
| 設定画面の保存（`--settings-window-probe`） | 既定は OFF・8 秒で書き出さない、3 と 8.5 は拒否、ON・12 秒は保存。ピル（`--pill-probe`）は新状態 `Flushing` でフォーカスを奪わず表示 |

### 未確認（実機・実マイク・外部サービスが要る部分）

- **発話での実マイク入力**: マイクの連続取り込みは無音・環境音でフレームの連続性までを確認しただけで、実際に話しながらの複数回入力は未確認。
- **本物のクラウド認識・整文サービス**: 認識は擬似サーバー（応答は識別子）で、実際の認識精度・区間の切れ目の語欠け・429 などは未確認。整文はプロセス内のモックで、互換/ChatGPT の実接続での区間整文は未確認。

- **画面の目視**: ピルの「残りを入力中」・設定画面の新しい欄の見た目・トレイのバルーン。
- **Hane 連携が有効な環境、ローカル認識**: 範囲外（後述）。
- 20 分連続の耐久、最大メモリ、実効処理時間の測定（§8）は未実施（S-8）。

## 設計からの逸脱・選択

1. **無音併用（VAD）は入れていない。** S-1 のタスク定義は固定秒数分割で、§2 も「固定間隔の最初のスライスでは VAD を入れない」とするため、区間は録音開始から目標間隔ちょうどで切る。最小 0.75 × T・最大 1.25 × T・300 ms 無音の中央といった数値は S-6 で使う（このスライスには定数も置いていない）。目標間隔の既定 8 秒・範囲 4〜20 秒は設計どおり。
2. **ストリーミングが有効でも、クラウド認識以外・Hane 連携が有効なときは一括にする。** ローカル認識は S-4（モデル固定・事前準備）、Hane は S-5 の範囲で、最小スライスに含めない（設計書のタスク定義に従った）。無理に通さず、その録音は従来の一括で処理し、控えめな通知で知らせる。ただし Hane 連携を有効にしている間は、Hane 以外のウィンドウでもストリーミングは使えない（Hane の対象かどうかは文脈取得の後でないと分からないため、設定の有効/無効で判断）。S-5 で解消する。
3. **投入失敗の集計。** 適用不明は「適用未確認」、入力先の不一致など確実に入っていない失敗は「欠落」として数える（設計 §6 は両方を別に数える前提だが、後者の呼び名は設計にない）。
4. **フラッシュ期限の起点** は「マイク解放」ではなく、区間の読み手がチャンネルの完了を観測した時点（実質同じ。差はミリ秒）。期限の点検は 250 ms 間隔（`StreamingLimits.Tick`）なので、期限は最大でその分遅れる。
5. **XAML アイランド（新しいメモ帳）の厳密確認** は、フォーカスが宛先の編集コントロール自体に見える状態も同じ入力先とみなす（設計は厳密一致。既存調査で、このクラスのフォーカスが交互に見えるため）。実機で未確認。
6. **リサンプラーは停止時に内部の遅延分を吐き出さない**（末尾の数 ms 未満が欠ける）。余韻回収 250 ms の後なので影響は小さい想定だが、測っていない。
7. `SessionState.Flushing`、`SessionSnapshot.IsStreaming`、`InjectResult.EffectUnknown`、`HeldKind.StreamingNotInjected`、`ITextInjector.InjectSegmentAsync`（既定実装つき）を公開 API に追加した。`Core` に `InternalsVisibleTo`（テスト用）を足した。

## S-4 以降への引き継ぎ

- **S-4（ローカル認識）**: 今は `RecognitionEngine.Local` のときストリーミングを使わず一括にしている（`TryBeginStreaming`）。`StartRecognitions` の同時数はローカルで 1 にしてあり、`WhisperRecognizer` の単一ワーカーを区間キューにつなぐ（モデル固定・事前準備・障害からの回復）際に、ここの分岐を外す。24 秒の認識期限とのコールド起動の関係は S-4 で確認する。
- **S-5（Hane）**: `HaneLinkReady()` が真のとき一括に倒している。`ReplaceJob` / 編集枠 / `HaneReplaced` の版・選択の連続性を足すときに外す。Hane 経路でも `Flushing`・集約通知・`StreamRun` の連番管理は流用できる。
- **S-6（VAD・重なり・認識ヒント）**: `SegmentSplitter` の `Push` / `Flush` の外側に、無音候補の選択（0.75T〜1.25T）と強制境界の前後 400 ms を足す構造にしてある。`RecognitionResult` に時刻が無いこと・`PcmFrame` が欠けを `StartSample` の不連続で表すことを前提にしている。
- **S-7（参考文）**: `StartPolishes` が `PolishInput(raw)` だけを渡している。「直前区間の確定テキスト末尾」は `StreamRun.LastChar` の隣に保持できる（今は末尾 1 文字だけ）。750 ms の待ちはここに入る。
- **クラウドの 429**: `Retry-After` を構造化して新規発行を止める処理は入れていない（今は失敗として欠落になり、自動再送もしない）。`CloudTranscriber` の戻りに待機指示を持たせる変更が要る。
- **メモリ予算**: 24 MB の事前照合は入れていない。上限は「保持 8 件」「リング 2 秒」と、PCM の解放（認識が終わり次第）で担保している。認識タスクは呼び出しが終わるまで自分の PCM を保持する。
- **S-8（測定）**: 診断 `--streaming-probe`（区間間隔・倍速・応答遅延・停止/取消・応答喪失の注入）と `--record-probe --streaming`、`WavStreamingRecorder` を耐久・故障注入の土台に使える。実機のメモ帳での厳密投入、実マイクでの複数回入力、実クラウドでの確認は S-8 の受け入れで行う。
