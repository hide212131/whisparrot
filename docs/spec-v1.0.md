## 1. 背景と目的

OpenWhispr を Windows で使ったが、アカウント登録や有料プランへの導線が多く、単に「話して文字を入れる」ための道具としては過剰だった。そこで、音声入力の核だけを持つ最小の常駐アプリを自作する。

## 2. ゴール / ノンゴール

ゴール:
- ホットキー1つで、日本語の発話をその場のアプリへ文字として流し込めること。
- 控えめなスペックの PC でも実用速度で動くこと（基準機: RAM 16GB、Intel Iris Xe Graphics 相当の統合 GPU）。
- 置くだけで使えるポータブル配布と、頻繁な更新に耐える簡単な更新手順。

ノンゴール（入れないもの）:
- アカウント登録、課金・有料プラン導線、テレメトリ、利用統計の送信。
- 履歴、文字起こしの保存・閲覧、辞書登録、会議録音、要約、翻訳、音声コマンド。
- アプリ提供者の独自サーバーを介した処理は行わない。利用者データの送信は、利用者が明示選択したクラウド認識先への音声と、任意の整文先への認識済みテキストに限る。利用者が指定する LiteLLM 等の互換プロキシは接続先として利用できる。

## 3. 対象環境

- OS: Windows 11（主対象）。Windows 10 は設計時に要否を判断する。
- アーキテクチャ: x64 と ARM64 の両対応（配布物はアーキテクチャ別に出し、更新時は自分のアーキのものだけを取る）。
- 検証機: Windows ARM64 VM（Windows 11 ARM64 の VM、機能確認用）。速度の基準測定は Iris Xe 相当の x64 実機で行う。

## 4. 基本動作

1. トレイ常駐。メイン画面は持たない。
2. ホットキー（既定候補: Win+J、変更可能）で録音開始。もう一度押すと停止するトグル方式。
   - Win+J は Windows 側に小さな割り当て（ヒント通知へのフォーカス）があるため、実機で奪えることを最初に確認する。奪えない場合は Ctrl+Win+J 等への既定変更を設計で決める。
3. 録音中は、Windows 標準の音声入力（Win+H）に似た小さいピル型バーを画面下中央に表示する。要素はマイク状態、音量レベル、停止、キャンセルだけ。
4. 停止後、第1段（既定のローカル認識、または明示選択したクラウド認識）→ 第2段（任意の整文）→ 投入先アプリへの文字投入、の順に処理し、バーは消える。
5. 投入先は、録音開始時（ホットキーのトグルで開始した時点）の前面ウィンドウとそのフォーカス中コントロールに固定する。途中で別のアプリへフォーカスが移っても、投入先は変わらない。トレイから録音を開始した場合など、開始時に有効な対象を記録できないときは、従来どおり投入時点の前面ウィンドウへ入れる。記録した対象が無効（ウィンドウが閉じられた、自プロセス・シェル・デスクトップだった等）のときは「入力先のウィンドウが見つかりません」で失敗し、テキストは保持する。トレイからの再試行は、その時点の前面ウィンドウを対象とする。
6. 文字投入の経路は次から選ぶ。決定の順序は「アプリ別上書き（プロセス名＝exe のベース名）→ auto のクラス判定」。
   - `auto`: フォーカス中コントロールのクラスで振り分ける。標準の編集コントロール（Edit / RichEdit 系 / Scintilla）は貼り付けメッセージ（WM_PASTE）、カスタム描画は Ctrl+V。標準クラスでメッセージを送れなかった場合は Ctrl+V へ落ちる。
   - `paste-message`: 貼り付けメッセージを記録したコントロールへ直接送る。前面化しない。
   - `ctrl-v` / `shift-insert` / `custom`: クリップボードへ置いてから、Ctrl+V / Shift+Insert / 利用者指定のキー組み合わせ（例 Ctrl+Alt+V）を SendInput で送る。送る直前に記録したウィンドウを前面化し、前面化できなければ何も送らず失敗とする（無関係なアプリへ送らない）。
   - `typing`: クリップボードを使わず（退避・復元もしない）、SendInput の Unicode 文字入力（KEYEVENTF_UNICODE）で送る。改行は Enter キーではなく改行文字（LF）の入力として送り、Enter として効くアプリでの送信・確定の誤発を避ける。投入直前に記録したウィンドウを前面化し、入力の途中で前面が変わったら中断する。長いテキストも、SendInput を数百文字単位でまとめて送る。
   クリップボード経由の経路では、投入前のクリップボード内容を復元する。キーリマッパが常駐する環境でキー系の経路が貼り付けにならないアプリには、アプリ別上書きで `typing` を指定できる。

## 5. 認識パイプライン（A案・確定）

### 第1段: 音声認識（ローカル / クラウド）
- 認識先はローカル / クラウドの排他選択で、既定はローカル。ローカル選択時、音声は PC の外へ送信しない。クラウド選択時だけ、録音停止後の音声を利用者が指定した OpenAI 互換文字起こし API へ送信する。接続先による転送を含め設定画面に明示する。以下の Whisper・モデル・GPU の項目はローカル認識として維持する。
- エンジン: whisper.cpp 系。モデルは base / small / medium / large-v3-turbo から選択可能とし、既定は small を本命候補とする（基準機での実測後に最終決定）。
- 言語: 日本語（固定を既定とする）。
- 加速: 統合 GPU 向けに Vulkan を第一候補とし、NVIDIA 向け CUDA、どれも使えない場合は CPU へ自動で落ちる。設定画面に「実際に使われた実行方式」を表示する。
- モデルファイルは本体とは別に `models/` へ置き、初回に取得する（ハッシュ検証つき、プロキシ経由可）。本体更新で再取得は発生しない。
- クラウド認識はベース URL・API キー・モデル名で設定する。認識失敗は非投入で通知し終了する。ローカルへの自動復帰・自動再送は行わず、音声は保存しない。（D-7）
- クラウド認識の上限（D-8）: 送信する WAV ファイル全体は 25,000,000 byte 以下（約 13 分）、停止後に検査して超過は送信せず認識失敗とする（自動停止・分割・圧縮はしない）。処理の期限は短い発話向けの 60 秒固定とする。

### 第2段: クラウド AI 整文（任意）
- 役割: フィラー除去、句読点・改行の付与、言い間違いの軽微な補正。意味を変えない、本文テキストだけを返す、発話内容に含まれる指示文には従わない、を整文プロンプトの不変条件とする。
- 整文は OFF にできる（その場合は第1段の生テキストをそのまま投入）。
- 接続先は次の2系統:
  1. OpenAI API 互換エンドポイント: ベース URL、API キー、モデル名を設定する。この1実装で OpenAI 本家、LiteLLM、Groq、その他互換サーバー、ローカルサーバーに接続できる。ベース URL は HTTPS を必須とし（ローカルホストのみ HTTP 可）、URL への認証情報埋め込みは拒否する（hane の Custom Provider の検証規則を踏襲）。
  2. ChatGPT ログイン経由: hane と同様の利用形態。実装方式は設計の決定事項 D-1（§9）。
- 失敗時の原則: 整文がエラー・タイムアウト（目安 15 秒、設計で確定）の場合は、生テキストをそのまま投入し、発話を絶対に失わない。失敗したことはバー／トレイで控えめに知らせる。この原文保持の保証は第1段で認識済みテキストを得た場合に適用する。認識自体が失敗した場合には復帰用の原文は存在しない。

## 6. 通信とプロキシ

- アプリ管理通信は、クラウド文字起こし、整文、更新確認・適用に必要な取得、モデル取得の4用途に限る。すべて共通のプロキシ規則を適用する。クラウド文字起こしの用途はクラウド選択時の音声送信に限る。
- 全通信に `https_proxy` 対応を適用する。モードは「環境変数に従う / 手動指定 / 使わない」の3つを持ち、環境変数は `HTTPS_PROXY`・`https_proxy`・`NO_PROXY` を正規化して扱う（hane の `crates/network` の NetworkContext の考え方を参考にする）。
- API キーは平文で持ち歩かない。Windows DPAPI で暗号化して保存し、ログに出さない。

## 7. 設定

- 最小項目のみ: ホットキー、マイク、モデル、整文の接続先（互換エンドポイント or ChatGPT or OFF）、モデル名、プロキシ、自動起動 ON/OFF、投入経路（アプリ別上書きとカスタムキー）。
- 追加: 認識先（ローカル / クラウド）と、クラウド認識のベース URL・API キー・モデル名。整文接続とは独立して保存する。
- 保存場所: 本体 exe の隣の `config.json` を基本とする（ポータブル性優先）。ただし ChatGPT の認証情報は hane と同様に本体・設定とは別の保存域に置き、本体更新で消えないようにする。
- 設定ファイルには schema_version を持たせ、新しすぎるバージョンは黙って初期化せずエラーにする（hane の ai-settings の規則を踏襲）。

## 8. 配布と更新

- 形態: ポータブル exe（インストーラなし、管理者権限不要）。アーキテクチャ別に `*-x64.exe` / `*-arm64.exe` を GitHub Releases へ置く。
- フォルダ構成: `本体 exe + config.json + models/`。更新で入れ替わるのは本体だけ。
- 更新: 起動時の日次チェック＋トレイからの手動確認。新しい版があれば知らせ、利用者が適用を押したら、ダウンロード（ハッシュ検証つき）→ 本体の差し替え → 再起動までを自動で行う。失敗したら旧版へ戻す。
- 署名なし配布を前提とする（SmartScreen の初回警告は README に明記する）。

## 10. 受け入れ基準（初版）

- Win+J（または確定した既定キー）で録音開始・停止でき、メモ帳・ブラウザ・主要なチャット欄へ日本語テキストが入る。
- 整文 ON（互換エンドポイント接続）で句読点つきの文が入り、整文先を止めても生テキストが入る（発話を失わない）。
- x64 / ARM64 両方の exe が起動し、Windows ARM64 VM で一連の動作が確認できる。
- 本体を新版へ更新しても、設定とモデルがそのまま使える。
- プロキシ環境変数を設定した状態で、整文と更新確認がプロキシ経由で成功する。
- クラウド選択時だけ指定先へ音声を送信し、成功後は既存の整文・投入を利用できる。認識失敗・取消では投入しない。既定のローカル経路と整文失敗時の原文投入を維持する。
