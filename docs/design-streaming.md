# whisparrot ストリーミング入力設計

> ずーっと喋り続けたら、ある一定秒間隔で一定数の認識整文した文字が出るようにしてほしい。ストリーミングのように。そのためには、認識・整文・出力を多重に行う必要があると思う。

録音を続けたまま、短い音声区間を順に確定する。認識先には区間単位で音声を渡し、後続区間の録音・認識と先行区間の整文・出力を重ねる。推奨は目標 8 秒、近くに無音があればそこで区切る方式。汎用経路は整文済みの区間を順に入力し、Hane は既存の原文先行設定を使う。区間当たりの文字数は話速と内容に応じて変わる。一定量ずつ出る体験は区間間隔で近づける。

設定と運用上限の数値は初期案。Hane 文書の抜粋・用語・要約を整文や認識へ渡す W-3 以降の設計は対象外。ストリーミングでは同じ録音セッション内の直前区間だけを整文の参考にする。一括モードとファイル入力は既存動作を継続する。

## 2. 音声区間の切り方

| 方式 | 利点 | 課題 |
| --- | --- | --- |
| 固定秒数 | 発行間隔が予測しやすく、負荷試験の再現性が高い。最初の実装に向く。 | 文中や単語の途中でも切れる。無音区間まで送ると費用と誤認識が増える。 |
| 無音（VAD） | 自然な休止で区切りやすい。 | 間を空けずに話すと出力が遅れる。休止が多いと細切れになりやすい。 |
| 固定秒数と VAD の併用（推奨） | 出力の間隔を保ちながら、文や語が切れる頻度を下げられる。 | 話速・ノイズによって間隔が揺れる。VAD の判定と強制境界を検証する必要がある。 |

- 16 kHz のサンプル位置を基準にする。目標を `T`、最小を `0.75 × T`、最大を `1.25 × T` とする。既定では 6〜10 秒。20 ms フレームで音声区間検出を行い、300 ms 以上続いた無音の中央を候補とする。目標到達時に確認済みの候補があれば目標に最も近いものを採用し、なければ上限までに確認できた最初の候補で切る。上限までに候補がなければ強制的に切る。停止時の末尾は最小長未満でも処理する。
- 区間長の起点は発話開始。無音だけの間は要求を発行せず、次の発話まで直近 200 ms を保持して語頭を回収する。VAD が区間を無音と判定した場合は送信を省く。小声・雑音で発話を誤って省く割合を評価し、固定間隔の最初のスライスでは VAD による省略を入れない。
- 文や単語の途中で別々に認識すると、Whisper が利用できる音響情報と前後の文脈が減り、語の欠落や誤認識が起きやすい。影響の大きさは実機で比較する。Whisper の参照実装には前ウィンドウの出力を認識のヒントにする機能と、単語時刻を返す機能がある。 [Whisper の参照実装](https://github.com/openai/whisper/blob/main/whisper/transcribe.py)
- 強制境界の候補として、境界前後 400 ms を両方の認識要求に含める。時刻を返せる場合は絶対音声時刻に変換し、単語の中心が属する半開区間に割り当てる。後続結果の境界付近は確定した直前区間の時刻・表記と照合し、同じ音声範囲に対応する同じ語の再出力を省く。前区間の認識が未確定なら境界整理だけを認識期限内で待ち、後続結果から投入済みの本文は変更しない。前区間の欠落が確定していれば、後区間に含まれる重なりから未出力の語を拾える。現在の `RecognitionResult` はテキストとバックエンド名だけで、`CloudTranscriber` も本文だけを使う。時刻を取れない接続先では初期は重なりなし。文字列の末尾・先頭一致による重複除去は、意図的な繰り返しや日本語の部分一致を誤って消さないかを比較してから採用する。
- 前区間の**認識原文の末尾**を最大 80 Unicode スカラー値で認識ヒントにする方式も比較する。認識ヒントは切断された音の回収を保証せず、誤認識の引き継ぎもあり得る。現行の `RecognitionRequest` と `WorkerProtocol` の `RequestHeader` にヒント欄はない。対応を確認したローカルワーカーで先に試し、並行するクラウド認識は初期はヒントなし。対応する方式を追加する場合も、認識開始時に直前区間が成功済みなら用いる。

## 3. 並行度、順序、整文入力

録音スロットをセッションに一つ持つ。各音声区間に `(sessionId, sequence)`（連番は 1 から）と音声時刻、区間確定時の単調時計、各段の状態を持たせる。バックグラウンドの完了・タイマーを識別子付きで `SessionCoordinator` に戻し、終端済み区間の遅い完了は破棄する。オーディオフレームは専用の有界バッファで受け、フレームごとに現行の無制限イベントチャネルへ積まない。

| 段 | 初期上限と根拠 |
| --- | --- |
| ローカル認識 | アプリ内で実行 1 件、モデル常駐ワーカー 1 台。既存ワーカーの前に順番付きキューを置く。small の常駐時 working set は過去の測定で約 0.8 GB。複数台ではモデルの複製や GPU/CPU の競合が起き、二台で約 1.6 GB はモデル常駐分の概算。単一ワーカーで、実効処理時間が音声区間長に追いつくかを測る。 [M1 実測](m1-report.md) |
| クラウド認識 | アプリ内で実行 2 件。1 件の応答待ちを次の区間の送信で隠しつつ、同時接続・転送・レート制限の影響を抑える。429 では自動再送せず、接続先の有効な `Retry-After`（なければ 8 秒）まで新規発行を止め、期限内に発行できなければ欠落として進める。現行の `TranscriptionResult` は HTTP 状態を持つが、`RecognizeAsync` では例外に変換され、待機指示も保持しない。区間用の呼び出しには 429 と待機指示を構造化して返す。 |
| 整文 | アプリ内で実行 2 件を Hane 差し替えジョブと汎用の整文で共有する。既存の Hane ジョブ上限に合わせ、録音区間の到着と外部応答の揺れを吸収する。Hane の確定待ちハンドルにも別途 2 件の上限を設ける。 |
| 出力 | アプリ内で同時 1 件。汎用はクリップボード復元まで、Hane は応答・同一 ID での照会まで次の出力を待つ。Hane の挿入と差し替えもこの枠を共有する。 |
| バッファ | 区間確定から出力の終端まで最大 8 件。入力中の 1 区間と、先行挿入後の Hane 差し替えジョブ最大 2 件は別枠。上限時に新たに切れた区間は連番を割り当てて欠落扱いとし、PCM を解放する。連続欠落は連番範囲と件数で圧縮し、録音やコールバックを待たせない。 |

認識待ちは締切の早い順（同一セッション内では連番順）に開始する。認識と整文の成功は完了した順に保存してよい。挿入は「次に扱う連番」からしか送出しない。先頭の区間が出力済み・欠落・無音のいずれかで確定したら進める。後続が先に完了しても追い越さない。Hane の先行挿入では原文挿入の確認で連番を進め、差し替えは元の範囲だけを更新する。

| 期限（単調時計） | 期限に達したとき |
| --- | --- |
| 区間確定から認識完了まで 24 秒。待ち行列・送信・ローカルの起動と既存の GPU → CPU フォールバックを含む。 | 区間の処理を取り消し、原文がないので欠落として進む。録音中に新規送信を止めるのは該当タスクのみ。ローカルのコールド起動が間に合わない場合に備え、録音開始時に非同期でワーカーを準備する。準備中の区間も同じ期限を適用し、連続する起動失敗時は準備を連打しない。 |
| 整文は開始から現行の `PolishSetup.Ready.Timeout`（15 秒）、かつ区間確定から 32 秒以内。整文枠と前区間の参考文を待つ時間も 32 秒に含む。 | 汎用と Hane の先行挿入 OFF は認識原文を出力候補にする。Hane の先行挿入 ON は原文を確定し差し替えを省く。 |
| 区間確定から 32 秒で、先頭区間を次段へ進める判断を確定する。 | 原文があれば原文、なければ欠落。すでに確定済みの整文結果は使う。32 秒はキュー内の認識・整文待ちの上限。送出済み出力の確定は経路固有の期限を使う。 |
| 区間確定から 40 秒で、出力枠を待っている未送出の区間を打ち切る。 | 欠落として次へ進む。すでに原文を挿入した Hane 区間は差し替えの送出を省き、現状を維持する。フラッシュの期限が先ならそちらに従う。 |

期限で結果を確定することと実行枠を空けることを分ける。HTTP の取消・ローカルワーカーの終了を要求し、実際に呼び出しが終了するまで枠を再利用しない。汎用投入のクリップボード処理も途中で枠を手放さない。終了通知は期限切れ後も枠の解放に使える。

整文開始時に、同じセッションの直前区間でアプリが入力を確認し確定したテキストの末尾を最大 200 Unicode スカラー値まで、参考文専用フィールドで渡す。汎用は投入成功を返した本文、Hane は差し替え確認済みの整文か、原文維持が確定した本文を使う。差し替え待ちの原文、未投入、適用不明、利用者の編集が検出された範囲は使わない。直前区間が処理中なら、現在区間が整文待ちに入ってから最大 750 ms だけ待つ。欠落や未確定なら参考文を省き、さらに前の区間へは戻らない。このため整文を直列化せず、後続の整文が先に完了しても出力順を保てる。

`PolishPrompts` では現在区間と参考文を別の入力フィールドにし、現在区間の内容だけを整え、参考文の再掲や言い足しを避けるよう指示する。認識後に重複整理を行ってから整文に渡す。区間末尾が文途中なら無理に文を補完しない。設定 UI に直前区間の末尾を設定済みの整文先へ送る旨を明示する。整文 OFF では送らない。Hane 文書文脈の送信設定とは独立した、同じ発話内の処理とする。

## 4. 経路別の出力

### 4.1 Hane

録音開始時の `StartHaneContext` で Hane の窓、インスタンス、文書、版、選択を取得する。取得の既存予算は 150 ms。先頭の出力までに経路を決め、以後そのセッション中は固定する。認証と対象取得に成功したら Hane 経路を使う。対象を取得できない場合の汎用投入も §4.2 の厳密な対象確認を通す。Hane から対象不一致を明示された場合は自動投入を止める。

**原文先行 ON。** 連番順に `edit.insert` で原文を挿入する。挿入確認後、区間 ID・範囲ハンドル付きの `ReplaceJob` で整文し、`edit.replace` で未変更の範囲を差し替える。録音スロットはそのまま使い、差し替えを録音終了まで保留する現行の `SessionBlocksReplace` の判定を区間用に変える。

- 編集操作は一度に一件。待機中の差し替えが準備できていれば、次の挿入より先に処理する。複数あれば古い連番を優先する。差し替え待ちが未完了なら次の原文を挿入できる。後ろの差し替えが先に完了しても、更新対象は挿入済みの範囲に限る。
- `MaxReplaceJobs` と `HaneContextRequest.MaxPendingHandles` は各 2 件のまま。挿入前に整文・追跡枠を確保し、空きがなければその区間は原文で確定して集計する。既存の一括モードの差し替えも同じ枠に含む。ハンドルは、変更なし・失敗・取消・差し替え確定でクライアントの追跡から外す。後続区間をハンドルの失効（既存契約では 120 秒）まで待たせない。整文 OFF の原文確定は通常動作として扱う。
- 挿入成功時は `HaneInserted.InsertedRevision` と挿入範囲の末尾を次の期待版・キャレットとする。差し替え成功後も、次の挿入にはアプリが確認した版と選択が必要になる。現行 `HaneReplaced` の差し替え後の範囲は、後続の原文がある場合に現在のキャレットを表さない。`context.get` で読み直した版・選択をそのまま採用すると、利用者が移動した先へ入力し得る。
- Hane 側には、差し替えと同じ編集ターンで差し替え直前の版・選択と直後の選択を返す任意機能を追加する案を推奨する。直後の版は既存応答を使う。直前の版・選択が最後に確認した値と一致した場合だけ、直後の値を次の挿入に引き継ぐ。差し替えの適否は既存の範囲検証で決める。`HaneClient.GetContextAsync` で接続時の `HaneHello.Features` を対象情報とともに保持し、編集前に対応を判定する。応答の原子性と機能フラグは Hane 側での検証が必要。差し替え拒否が明示された場合は、その操作の前の期待値で次の挿入を試せる。変更があれば既存の `edit.insert` の検証で拒否される。
- 差し替えで版・選択の連続性が確認できない場合、挿入先の変更が検出された場合、編集の適用有無が不明な場合は、以降の自動挿入を止める。対象変更・適用不明をすぐ知らせ、既存の `HeldText` に直近一件のコピー候補を保持して §6 の停止処理に入る。通信不明時は `HaneClient` の既存の同一操作 ID・同一ペイロードでの一度の照会を使う。別 ID や汎用貼り付けに切り替えない。
- Undo は区間ごと。差し替えと元の挿入が既存の条件で結合できる場合は 1 回。間に次の区間や利用者の編集があれば独立の Undo になる。

**原文先行 OFF。** 汎用と同じく整文または原文フォールバックを待ち、Hane の `edit.insert` で一度入力する。ストリーミング用の差し替え応答に対応していない Hane でもこの方式を使い、原文先行設定が ON の場合はセッション開始時に切り替えを知らせる。先行挿入がない場合も、旧セッションの差し替えで期待版が変わらないよう、旧 Hane の同一文書の旧ジョブは現在のストリーミング期間だけ保留し、期限を過ぎたら原文を維持する。新機能のある Hane では旧ジョブの編集も同じ出力枠と版・選択の確認を通す。

### 4.2 汎用

整文完了を待ってから区間順に投入する。整文 OFF、失敗、時間切れでは原文を確定して一度だけ投入する。原文先行では後から整文結果を反映できないため、通常動作としては採用しない。

- 録音開始時に有効な `RecordedTarget` が必要。ストリーミングでは前景・PID・フォーカス中のコントロールと解決した投入先を投入直前まで検証する。対象の再解決による代替コントロールへの投入、別の前景への投入、記録した窓の自動前景化を避ける。保証できる範囲は OS が観測できる入力先まで。同じコントロール内の文書やカーソル位置の変更は検出できない場合があるため、録音中は入力先とカーソルを保つ旨を設定画面に表示する。
- `TextInjector.InjectCore` のストリーミング経路では、クリップボード書き込み前と実際のキーまたは貼り付けメッセージ送出直前に対象を確認する。現行 Auto は `WM_PASTE` が時間切れでもキー送信にフォールバックし得る。ストリーミングでは、送出の可能性がある時点から別経路への送出を省き、適用不明として扱う。汎用の成功は投入操作を送れたことを表し、受け手の文書を読み戻して検証した結果ではない。
- 入力先の不一致、送出の失敗・適用不明時は以降の自動投入を止める。投入できなかった、または未確認の直近一件をコピー候補として扱う。現行の `Failed` からの再投入にストリーミング区間を渡さない。

両経路とも区間ごとに改行を強制しない。初期は連続する英数字の境界に必要な空白を 1 個だけ補い、日本語の境界には原則そのまま続ける。空白補完は音声境界で分断された語も対象になり得るため、境界評価に含める。Hane の原文先行では挿入時の区切りを差し替えでも維持し、先に入力した区間を変更しない。句読点・Markdown・利用者が意図した改行は各区間の中に残す。

### 4.3 ピル

録音中は従来のマイクレベルを表示し、認識中・整文中の区間数や未確定の本文は表示しない案を推奨する。録音と過去区間の処理が同時に進むため、区間の段階ごとにピルを切り替えると録音の継続が分かりにくい。停止後だけ「残りを入力中」を表示し、取消を使えるようにする。`SessionSnapshot` のストリーミング状態を `TrayApp` から `PillWindow` に渡す。対象変更など、利用者の操作が必要な事象はその場で通知する。

## 5. 開始・停止・取消

| 操作 | 動作 |
| --- | --- |
| 開始 | 設定、マイク、認識・整文先、入力対象を記録し、セッション ID を発行する。対象が記録できなければ録音開始前に案内する。最初の区間が確定次第パイプラインへ流す。 |
| 停止 | ホットキーの再押下と停止操作で新規取り込みを終了し、`WasapiRecorder` の既存の余韻回収（250 ms）を上限内で行う。残りの PCM で最後の短い区間を一度だけ確定し、既存の待ち行列と Hane 差し替えを流す。ピルを「残りを入力中」に切り替え、新規録音はフラッシュ完了後に受ける。 |
| フラッシュの期限 | マイク解放から 25 秒で、残りの認識・整文期限を打ち切る。原文または整文がすでにある区間は、そこから最大 5 秒の送出枠で順に入力する。未送出の残りは欠落として集計し、送出済みの一件は経路の確定・後片付けを待つ。Hane で期限内に差し替えを送れなければ現状を維持する。 |
| 取消 | 取り込みを直ちに停止し、未出力区間の PCM・テキスト、送出前の差し替えを捨てる。同一セッションの認識と整文に取消を要求する。ローカルで実行中なら既存どおりワーカーを終了する。別セッションの既存 Hane ジョブは残す。 |
| 取消と送出の競合 | 段の切り替えと編集開始の許可はコーディネーターが直列化する。汎用投入は副作用直前、Hane は編集要求発行直前まで取消可能とし、発行後は一件の確定処理を続ける。UI は「取消しました。入力済みの内容は残ります」と表示し、送出中なら「送信済みの入力は反映される場合があります」を添える。Hane の差し替えが未送出なら原文が残る。 |

## 6. 失敗と通知

| 事象 | 区間とセッションの扱い |
| --- | --- |
| 認識失敗・認識期限切れ | その区間を欠落とし、次の区間へ進む。空の認識結果は VAD で発話が確認できた区間なら欠落、音声なしと判断できる区間なら無出力。固定分割で判別できない場合は空件数を別に記録する。クラウドの自動再試行は行わず、ローカルの既存 GPU → CPU フォールバックは認識期限内に限る。 |
| 整文失敗・時間切れ・空結果・枠不足 | 原文を入力または維持して次へ進む。ストリーミングによる再試行は追加しない。既存の認証更新など接続単位の回復はその呼び出しの期限と枠を消費する。 |
| Hane の範囲変更・失効 | 原文または利用者の編集を維持する。整文結果は直近一件のコピー候補にできる。後続の挿入は最後に確認した版・選択の検証を通す。 |
| 入力先の変更・編集の適用不明 | 自動投入を停止し、利用者に入力先の確認を案内する。送出中の一件を確定処理し、新規認識・整文と未出力分は打ち切る。未投入・適用未確認の直近一件だけをメモリに保持し、明示コピー・破棄・既存の保持期限で解放する。 |
| マイク切断 | 新しい録音を止め、録音から確実に回収できた区間と確定済み区間はフラッシュする。音声の欠損をまたぐ区間を失敗として集計する。 |

区間ごとの警告はピルに連続表示せず、完了時に「入力 24 区間・原文のまま 2 区間・欠落 1 区間」のように集約する。原文件数は入力済み件数の内訳。取消による破棄と適用未確認は別に数える。原文維持や欠落が連続 3 区間に達した場合は、録音中にも各理由をセッションにつき一度だけ通知する。入力先変更・マイク切断・連続録音上限はその場で通知する。

## 7. 上限、メモリ、クラウド費用

- **録音は 1 回 20 分まで。** 停止の余韻を含めた上限としてマイクを解放し、上限到達を通知してフラッシュする。4 秒設定時の最小区間は 3 秒なので、停止末尾込みで最大約 400 区間。必要な場合は前のフラッシュが終わってから次の録音を始められる。
- **保持メモリは区間数とバイト数で制限。** 16 kHz mono float の PCM は 64,000 byte/秒。最大設定の 25 秒に強制境界の前後最大 0.8 秒を加えると、処理中最大 8 区間と収集中 1 区間の PCM は約 15 MB。キャプチャ側のリングは最大 2 秒、PCM・一時コピー・WAV・ワーカーへの送信用コピーを合わせた親プロセスの録音・送信用音声バッファは初期 24 MB を予算とする。確保前に上限を照合し、過負荷時は PCM の新規受け入れを省いて欠落箇所を数える。認識タスクが実際に終了するまでは所有バイトを解放済みと数えない。ローカルモデル、HTTP 内部バッファや応答本文はこの概算とは別で、既存の応答サイズ上限と同時実行数で制限し、実測対象にする。
- **滞留を増やし続けない。** 認識後の PCM は各段が所有しなくなり次第解放する。確定済みの区間は本文を連結して蓄積せず、直前区間の参考文、境界比較に必要な末尾、通知の件数、直近一件のコピー候補のみを保持する。デバイスやリサンプラーに入力欠損が出た場合は音声時刻の不連続を記録し、境界重複の判定と前区間ヒントをそこからリセットする。音声・本文・認証情報は診断に出さず、音声は作業ファイルへ書き出さない。
- **クラウド認識の費用は送信秒数と要求単位の課金・丸め次第。** 連続して 20 分話すと 8 秒設定で約 150 件、4 秒で約 300 件。毎回 0.8 秒の重なりを送る場合、音声量は 8 秒設定で約 10% 増える。無音省略で減る可能性がある一方、区間ごとの最低課金やリクエスト制限がある接続先では短い区間ほど影響が大きい。現行の `WavEncoder` の 25,000,000 byte 上限は要求単位に適用し、録音全体の上限とは別に扱う。
- **外部整文は区間ごとに指示と参考文の分が加わる。** 整文 ON では長時間一括に比べ呼び出し回数が増え、同じ指示と最大 200 文字の前文を繰り返し送り得る。測定では送信音声秒数、要求数、応答コード、取得できる場合はトークン使用量を記録し、料金換算は利用先とモデルごとの条件を使う。クラウド認識 ON では録音中から送信が始まることを設定画面に表示する。

## 8. 精度と速度の測定

一括と区間処理に同じ音声を入力する。短い音声と、20 分連続の負荷音声を用意する。一括クラウドとの比較は既存 WAV 上限内の音声で行い、20 分音声はストリーミングの耐久試験に使う。複数話者の自然な発話、小声・雑音、長い無音、休止なし、境界をまたぐ語・固有名詞、句読点、同じ語の意図的な繰り返し、数字・否定を含む日本語音声を使う。正解の文字列と語の境界、正解に残すべき数字・固有名詞を事前に記録する。

| 比較 | 記録する指標 |
| --- | --- |
| 一括、固定 4 / 8 / 12 / 20 秒、VAD のみ、併用 4 / 8 / 12 / 20 秒 | 認識原文と最終出力を別々に評価。文字誤り率（置換・削除・挿入の合計 / 正解文字数）、固有名詞の正表記率、数字・否定の改変件数、境界付近の欠落・重複、無音省略による発話の欠落。欠落した区間も正解に対する削除に含める。原文の CER は空白や句読点を外した値も併記し、最終出力は整文済みの別参照と比較する。 |
| 選んだ長さで重なりなし / あり、認識ヒントなし / あり、整文参考文なし / あり | 一度に一条件を変え、境界の欠落・重複、表記の連続性、意図的な反復の誤削除を計測する。整文参考文の取得率、待ち時間、参考文が出力に混入した件数も測る。 |
| ローカル（CPU / GPU、コールド / ウォーム）、クラウド（通常 / 遅延・429）、Hane / 汎用 | 発話開始から初回表示、音声区間末尾から表示・確定、出力間隔、話し終わりから最後の区間の表示と最終確定までの p50 / p95。停止操作から最終確定までを別に測る。Hane の原文表示と差し替え完了は別時刻。汎用はアプリ側の投入完了と Windows 実機のテスト対象で実測した表示を区別する。 |
| 20 分耐久と故障注入 | 各段の実行時間と待ち時間、滞留の最大値、欠落率、原文率、レート制限、要求数、音声秒数、最大メモリ。順序逆転、期限後の二重投入、対象変更後の投入、取消後の新規送出が 0 件であることを確認する。 |

入力機器、PCM、モデル、言語、整文指示、接続先、出力先を条件内で揃える。Whisper の実効処理時間 / 音声区間長が 1 以上の状態で続くかを調べる。初期の採用目安は、通常条件の既定 8 秒で最終区間末尾から確定まで p95 12 秒以下、連続発話中の確定出力間隔 p95 16 秒以下、認識原文 CER の増加が一括比 2 ポイント以内、固有名詞の正表記率の低下が 5 ポイント以内。値は測定目標であり、機種や外部接続先での達成は未検証。故障注入と耐久測定では §3 と §7 の上限を超えないことを別に判定する。

## 10. 利用者に決めてほしいこと

| 判断 | 推奨 |
| --- | --- |
| 区間の切り方 | **8 秒を目標に無音で調整。** 録音中も結果を出しつつ文途中の切断を抑えられる。厳密な発行間隔を重視する場合は固定秒数を選ぶ。最終判断は §8 の境界精度と間隔の比較で行う。 |
| 汎用経路で先に見せる内容 | **整文が終わった区間から順に投入。** 原文先行を選ぶと表示は早まるが、汎用経路ではその原文が確定本文になる。 |
| 録音中の途中表示 | **マイクレベルのみ。** 確定した内容は入力先で確認でき、停止後はピルの「残りを入力中」で処理の継続が分かる。録音中に滞留を知りたい場合だけ、未処理区間数の表示を選ぶ。 |
