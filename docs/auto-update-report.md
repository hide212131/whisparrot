# 自動更新 実装レポート

ブランチ: `feat/auto-update`（main 90ae434 から分岐）。push・マージ・タグ・リリースは行っていない。

## 実装
- **確認**（`Infrastructure/Update/ReleaseClient`, `UpdateService`）: 起動 5 秒後と、その後 24 時間ごと（`auto_check` が ON のときだけ）に `GET /repos/hide212131/whisparrot/releases` を確認。手動確認は設定画面とトレイの「更新を確認」。通信は既存の `NetworkContext`（`NetworkPurpose.Update`。プロキシ設定・HTTPS 固定・GitHub ホストのみ転送可）。確認の失敗は通知せず、状態も変えない（`updates.last_check_*` は既存の項目に記録）。`/releases/latest` はプレリリースを返さないため一覧を取る。
- **版比較・候補選択**（`Core/Update`）: `SemVer`（SemVer 2.0 の優先順位。プレリリース識別子の数値/英字比較、`v` 接頭辞・`+` 以降は無視）。`ReleaseSelector` は draft を除外、`prerelease` フラグまたはタグの `-` 付きをプレリリースとみなし、チャンネル設定に従って、現在より新しい最大の版を選ぶ。資産は `whisparrot*-<arch>.exe`（実在名 `whisparrot-win-x64.exe` / `-arm64.exe`）で、arch は `RuntimeInformation.ProcessArchitecture`。複数一致・別 arch・digest が無い/不正な資産は候補にしない（その場合は次点の版を見る）。
- **取得・照合**: ユーザーが「ダウンロード」を押してから、`<exe>.new.part` へ取得 → サイズと GitHub の資産 `digest`（`sha256:<hex>`）を照合 → 一致したときだけ `<exe>.new` へ。不一致・失敗では一時ファイルを消し、設定画面とトレイに理由を出す（再試行可）。
- **入れ替え**（`Core/Update/ExeSwap.cs`、補助プロセスなし）: ①`<exe>` → `<exe>.old` にリネーム ②`<exe>.new` → `<exe>` ③新版を `--after-update` 付きで起動、のあと旧プロセスは終了。どこで失敗しても逆順に戻し、旧版が元のパスに残る（戻せない場合は `.old` の場所と手順を通知）。「再起動して更新」は設定画面とトレイから。入力処理中（Idle 以外・未投入あり）は適用しない。新版は旧プロセスの mutex 解放を最大 15 秒待つ。
- **旧版の片付け**: 再起動直後の起動がトレイ・ホットキー登録まで進んだら `<exe>.update-ok` を作る。**次回の通常起動**で、その印があるときだけ `.old` と印を削除する。印が無いまま `.old` が残っているとき（新版が正常に起動しなかった可能性）は消さない。未適用の `.new` は通常起動のたびに捨てる。
- **設定**: `updates.auto_check`（既定 true）、`updates.include_prerelease`（既定 true）。既定値のときは書き出さない（旧版が未知キーを拒否するため。hane と同じ流儀）。欠損は既定で補う。`schema_version` は 1 のまま。設計書の設定表に 2 行追加。設定画面の「起動・更新」に 2 つのチェックボックス、「更新を確認」、状態表示、「ダウンロード」/「再起動して更新」を追加。プレリリースの切替を保存すると候補を取り直す。
- **診断**: `--update-probe check|apply-real|apply-local <exe>`（実機確認用。トレイと同じ `UpdateService`/`ExeSwapper` を使う）。

## 実機で見つけた問題（修正済み）
単一ファイル exe は、実行中にリネームした後は、まだ読み込んでいないアセンブリ（`System.Diagnostics.Process`、`Win32Exception` の `System.ComponentModel.Primitives`）を読めず `FileNotFoundException` になる（最初の実機試行は、この理由で「入れ替え後の起動」に入る前に巻き戻った）。`UpdateLauncher.Preload()` で入れ替え前に必要な型を読み込む。巻き戻し側は CoreLib の `File.Move` だけなので影響を受けない（旧版が残ることは、この失敗時にも確認できた）。

## 実地確認（検証機 Windows ARM64、cpu ビルド。旧版 = 0.2.0、新版 = 0.9.0 のこのブランチのビルド）
| # | 内容 | 結果 |
|---|---|---|
| 1 | 実在の GitHub への確認 | 取得できた。0.2.0 から候補 `v0.4.0-preview.3`（arm64 資産、74,037,504 bytes、digest 一致）。`--stable` では候補なし |
| 2 | 実在リリースの更新を最後まで（`apply-real`） | ダウンロード 約 3〜7 秒 → 照合 OK → 入れ替え `Swapped`。exe は GitHub の digest と同一（`d7845395…`）、`.old` が旧版、新プロセスが起動 |
| 3 | 自前の 2 版で入れ替え → 新版が `--after-update` で起動 → 印作成 → 次回通常起動 | exe が 0.9.0（ハッシュ一致）、0.9.0 が実行中、`.old`＋印が残る。次の通常起動で `.old` と印が消えた |
| 4 | 失敗: 起動できない新 exe（ゴミファイル） | `RolledBack`（Win32Exception）。旧 exe のハッシュは不変で、そのまま起動・動作 |
| 5 | 失敗: 残骸 `.old` が他プロセスにロックされている | `RolledBack`（IOException）。何もリネームされず旧版のまま |

## 未確認・限界
- **トレイ・設定画面の UI は実機で操作していない**。検証機の SSH セッションは対話デスクトップではなく（ホットキー登録も失敗する）、クリック操作ができない。画面部分（バルーン通知・メニュー項目・設定のボタン/状態表示）はビルドと全テストの通過のみで、目視・操作の確認はしていない。入れ替えと取得の中身は、トレイと同じ `UpdateService`/`ExeSwapper` を診断コマンドから通して確認した。
- ダイジェスト不一致の「ダウンロード中の破棄」は、実ネットワークでは再現していない（GitHub の配布物を改ざんできないため）。照合関数（`VerifyFileAsync`）とサービスの失敗表示は単体テストで確認。`DownloadAsync` の `.part` 削除は実行確認していない。
- 新版が起動後にクラッシュする場合の自動復旧はない（`.old` が残り、手動で戻せる）。旧版へ戻すのは入れ替え処理の途中失敗に限る。
- x64 の実機ビルドと、入力処理中（録音中など）に更新を押した場合の動作は未確認。
- 検証に使った 0.2.0 / 0.9.0 は検証機のみのビルドで、リリースしていない。実在リリースの更新（#2）は検証機の作業フォルダ内の exe を置き換えた（開発ツリーや利用中の導入には触れていない）。
- 署名・証明書は扱っていない（未署名のまま）。ダイジェストは GitHub が配る値で、配布アカウント侵害への真正性証明ではなく、破損・取り違えの検出である。
